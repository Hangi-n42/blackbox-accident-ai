# V6A 이후 허용 가능한 단일 대조 검토

검토 범위는 V6A 개발 00000/00003/00004의 원시 응답·제시 mosaic 및 소스다. 예약 GT/예측은 읽지 않았고 모델/GPU를 실행하지 않았다. 기존 파일을 변경하지 않았다.

**결론: 같은 후보와 같은 질문의 multi-image 제시 대조 한 번은 타당하다. 현재 결과는 학습이 반드시 필요하다는 증거가 아니다. 다만 이 대조는 표현 방식 전체의 차이를 검사하며, 시간 순서 인식만의 순수 효과나 해상도 동일 효과로 해석하면 안 된다.** 실패 시 이 개발 3개에서 문구·윈도·후처리를 추가 탐색하지 않는 중단 규칙이 필요하다.

## 현재 증거가 말하는 범위

`contact_verify_v6a_development/report.json`에서 세 영상 모두 18개 후보를 제시했다. 00000은 JSON null을 반환해 기존 motion 587을 유지했다. 00003과 00004는 각각 유효한 offered 정수 615, 1044를 반환했다. 따라서 뒤의 두 사례는 JSON 형식 오류나 snap으로 잘못된 답이 생긴 경우가 아니다. root가 확인한 사람 참조의 ±0.3초 내 프레임이 세 후보 집합에 포함된다는 조건하에서, 현재 개발 오류는 후보 안의 선택 단계에 남는다.

00004의 실제 제시 mosaic을 확인했다. 초반 창의 588부터 우측 차량이 크게 나타나고 이후 창에는 그 차량과 앞쪽 다른 흰 차량이 보인다. 이 이미지만으로 최초 물리 접촉을 새로 판정하거나 모델이 흰 차량을 상대라고 오인했다고 확정하지 않는다. 후반 1044 선택은 시간/상대 연계 실패와 양립하지만, 원시 JSON에는 이유나 대상 ID가 없으므로 원인을 개별적으로 식별할 수 없다. 접촉이 화면 밖이라면 동일 이미지 재배열만으로 직접 접촉 증거가 새로 생기지도 않는다.

## 제안은 하나: 기존 labeled tile을 개별 image로 분리

V6A의 후보·순서·프레임 번호·질문 문자열·48 출력 토큰·strict parser·null fallback·원 V5의 다른 세 출력·모델을 그대로 고정한다. 기존 384×256 labeled tile을 정확히 보존해 후보마다 하나의 image로 전달한다. `base._sheet(paths,[index],columns=1)`은 같은 원본 contain과 번호 글씨를 사용하므로, CPU에서 기존 mosaic의 해당 tile과 픽셀 일치를 먼저 확인할 수 있다. 실제 candidate 변경은 마지막 한 ask의 이미지 목록뿐이어야 한다.

원본 고해상도 프레임에 새로운 label bar를 얹는 변경은 이번 단일 대조에서는 권하지 않는다. 초기 resize 횟수·라벨 크기·padding·유효 화상 면적까지 한 번에 바뀌어, 이전 mosaic과 무엇이 달라졌는지 더 혼합된다. crop/reference/추적/새 상태 schema도 추가하지 않는다.

고정 근거:

- `candidates/stage2_contact_verify_v6a.py:29`: frozen baseline 결과를 재사용하는 refine 함수.
- 같은 파일 `:42`: 질문 및 offered 목록, `:53`: 한 mosaic ask, `:61`: strict offered 정수 검사.
- 실제 V5 `model/stage2/code/solution/stage2_v2.py:25`: `_sheet`, `:28`: 384×256 tile, `:33`: 원본 contain, `:35`: frame label.
- 실제 V5 `model/stage2/code/solution/vlm.py:29`: 이미지 개수로 총 pixel budget을 나눔, `:36`: 이미지마다 32배수 resize, `:37`: 이미지별 content item, `:41`: processor 입력.

## 같은 1.2MP 상한의 한계

현재 개발 3개의 실제 mosaic은 1920×1024이다. 기존 LocalVLM 전처리 식을 그대로 계산하면 다음과 같다. 모델 추론 결과가 아닌 결정적 크기 계산이다.

| 입력 | LocalVLM이 processor에 넘기는 크기 | 실제 합계 pixel |
|---|---|---:|
| 18 tile mosaic 한 장 | 1472×800 한 장 | 1,177,600 |
| 동일 tile 18장을 별개 이미지로 전달 | 각 288×192 | 995,328 |

즉 cap은 같지만 32배수 내림, 비어 있는 mosaic 칸, 이미지별 resize 때문에 실제 해상도·면적은 같지 않다. 별개 이미지가 더 선명해진다고 예고할 수 없다. 이 차이를 제거하려고 새 pixel budget을 사후 조절하면 또 다른 후보가 된다. 이번에는 cap을 그대로 유지하고 차이를 기록하는 편이 낫다.

또한 현재 `LocalVLM.ask`는 각 image item 뒤에 질문 텍스트 하나를 붙인다. 별개 이미지를 준다고 native video 입력이나 실제 PTS temporal encoding으로 바뀌는 것은 아니다. 이미지 경계·위치 구조·빈 영역·리사이즈가 함께 바뀐 presentation 대조다. 처리 시간과 VRAM도 이미지 개수 또는 pixel 합계만으로 보장하지 않는다.

## 실행 전 고정 및 판정

CPU 계약으로 후보 원본번호/정렬/두 중심 보존, 기존 tile과 제시 전 RGB 완전 일치, 같은 prompt bytes/토큰/parser/fallback, 기존 다른 세 필드 완전 동일, 마지막 호출 한 번 및 파일별 독립성을 확인한다. 출력 후 바꿀 수 없도록 소스·모델·입력·예산·gate를 동결한다.

개발 세 영상의 기존 baseline 캐시로 추가 호출을 각 한 번만 실행한다. 기존 gate를 유지하며 개선이 없으면 예약 예측을 열지 않는다. 유효 정수 선택으로 새로 맞은 사례와 null fallback으로 baseline 성공을 유지한 사례를 분리한다. 제시 전/후 크기, 실제 processor image grid와 입력 토큰 길이, call 시간/VRAM, 원시 응답, 후보 coverage를 기록한다. cap 동일을 실제 토큰 수 동일로 간주하지 않는다.

이 대조가 통과해도 개발·예약 각 세 사례의 작은 파일별 비교 근거다. 통과 뒤에만 동결된 후보로 예약을 한 번 확인하며, 정답 미확인 세 항목이나 전체 대회 점수 개선으로 확대하지 않는다. 실패한다면 현재 zero-shot 선택기가 이 표현 변경만으로 해결되지 않았다는 결론으로 멈춘다. 그때 필요한 것은 학습 여부를 구호로 정하는 일이 아니라, 충분한 대상·접촉 정답과 관측 가능한 정보가 포함된 데이터에서 시각 표현 또는 지도 학습을 별도 검증하는 일이다. 이번 후속에 두 번째 후보를 끼워 넣지 않는다.
