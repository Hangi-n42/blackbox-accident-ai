# 정식 영상 입력 경로의 실제 비교 결과

**고정한 9회 실행은 완료했지만 V7 채택 기준에 실패했다.** 사람 검수 초안에 대한 접촉 정답은 V6 최종 출력 4/9에서 영상 선택기 1/9로 감소했다. 새 정답 1개(00007)를 얻고 기존 정답 4개(00000/00003/00006/00008)를 잃었다. MAE는 3.732317초에서 11.692379초로 증가했다. 형식 오류나 fallback은 없었으며 9개 모두 제공된 번호를 반환했다.

## 무엇을 시험했는가

기존의 개별 이미지 실험은 V6B에서 이미 실패했다. 이번에는 같은 V6 두 번째 질문의 후보를 실제 Qwen video tensor로 전달했다. 두 프레임씩 묶는 temporal patch와 video modality를 사용한 첫 시험이다. 원본 후보 번호·순서·라벨 타일·4B NF4 가중치·48 출력 토큰은 유지했다.

입력에는 합성 2fps 재생 순서를 명시했다. 원본 FPS라고 주장하거나 출력 번호를 synthetic seconds로 환산하지 않았다. 실제 평가에는 원본 PTS를 사용했다. 영상 입력 설명문, 시간 토큰, 프레임 묶음, 유효 픽셀/토큰 수가 함께 달라지므로 순수한 배치 변경 하나의 인과효과로 해석할 수 없다. 후보 밖/불량 출력은 V6 최종 motion으로 복귀하는 사전 규칙이었지만 실제 fallback은 0개였다.

## 후보 누락과 선택 실패를 구분한다

고정 후보에 정답 ±0.3초 구간이 있었던 영상은 5/9개다. 기존 내부 VLM 선택은 0/9, 새 영상 선택은 1/9였다. 즉 **후보가 있는 5개 중에서도 4개를 잘못 골랐다.**

00003/00006/00008은 V6 최종 motion 출력은 맞았지만 기존 VLM 후보에는 허용 구간이 없었다. 이 세 영상에서 후보 안의 번호를 강제로 반환하는 선택기는 정답을 낼 수 없다. 그러므로 최종 4/9→1/9 하락을 전부 native video 표현의 열등함으로 해석하면 안 된다. 이번 고정 후보 실험은 후보 누락을 고친 완성 모델이 아니다. 반대로 내부 선택 0→1 한 건만으로 새 구조의 일반화 개선을 주장할 수도 없다.

진입·방향·공간은 이번 진단에서 V6 캐시를 복사했다. 해당 세 항목의 개선이나 전체 네 질문 파이프라인 검증을 수행했다고 부르지 않는다.

## 실행과 자원

- 모델 로드 1회, 실제 생성 9회, 외부 연결 시도 0회, 종료 코드 0.
- 실행 구간 42.163초. 사전 소스 검사 시간은 이 값에 포함되지 않는다.
- 영상 입력 준비·생성 호출 합계 15.421초, 과거 원래 두 번째 질문 호출 기록 합계 20.508초. 서로 다른 시점의 로컬 기록이므로 엄밀한 속도 개선 측정이나 전체 서버 60분 통과 근거가 아니다.
- GPU peak allocated 3,464,531,968바이트, peak reserved 3,605,004,288바이트. 각 호출의 peak 최댓값이며 GPU 전체 점유량을 뜻하지 않는다.
- CPU processor 검사에서 후보 보존, 홀수 마지막 프레임 패딩, 패딩 포함 1.2MP 상한, 원본 번호와 합성 시각 분리를 확인했다. 실제 호출에서도 같은 검사를 적용했다.
- 소스·모델·입력 바인딩은 실행 종료까지 불변이었다.

독립 검토에서 소형 동결 파일 160개와 선택 원본 PNG 132개의 SHA 및 후보·패딩·다른 세 출력 대응을 확인했다. 모델 로더가 상속한 `runtime.ask_implementation` 설명은 기존 image 경로 문구로 남아 있지만, 실제 실행 helper와 각 호출의 video tensor/grid 기록은 정식 영상 경로를 입증한다. 이 메타데이터 설명을 실제 호출 방식의 증거로 사용하지 않는다.
