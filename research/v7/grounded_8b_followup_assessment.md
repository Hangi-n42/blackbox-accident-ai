# 8B unified 이후 사후 혼합안의 독립 검토

2026-09-15. **현재 단계에서 “V6 motion contact + 8B unified의 나머지 세 출력”을 추가 구현·채택하는 안에 반대한다.** 서로 다른 예측기를 항목별로 결합하는 구조 자체가 잘못은 아니다. 그러나 이번 조합은 실패 결과를 확인한 뒤 좋은 항목을 남기는 새 가설이며, 원래 실패한 실험의 통과로 재분류할 수 없다. 동일 상대·진입·공간 문맥 결함과 실제 시간 비용이 남아 있다. 새 모델 실행·라벨·코드 변경은 하지 않았다.

## 1. 첫 계획의 실패는 미완성 JSON이 아니다

`grounded_8b_run/report.json`의 첫 원응답 9개를 직접 JSON 파싱했다. 모두 `contact`, `entry`, `reference_frame`, `bbox`, `target` 다섯 키를 가진 완성된 객체이며 마지막 문자는 `}`다. 9/9에서 contact와 entry는 `[null,null,null]`, bbox는 네 좌표 모두 null이다. reference_frame은 6개 null, 3개 유효 번호지만 bbox는 모두 무효다. 원응답 길이는 144~149자다.

따라서 **120토큰에서 JSON이 중간에 끊겨 계획이 사라졌다는 근거는 없다.** 실제 finish_reason·생성 token 수는 현재 기록되지 않았으므로 종료 원인까지 단정하지 않는다. 하지만 모든 요구 키를 완성해 null로 반환한 현상은 분명하다. `grounded_8b_protocol.json`의 실패 시 재튜닝 금지에 따라 이 결과를 근거로 토큰·문구·schema를 다시 탐색하지 않는다.

## 2. 방향 점수 상승과 실제 제시 영상

기존 사용자 방향 7개에서 4B V6 3/7·Macro-F1 0.4167에서 8B unified 5/7·0.65로 상승했다. 추가 일치는 00000·00005이며 둘 다 LEFT다. 이전 방향 정답 손실은 없다. 그러나 전체 출력은 **LEFT 8개, RIGHT는 00004 한 개**다. RIGHT 정답인 00008·00013은 계속 틀렸다. 공간은 9/9 실제 원응답 0, 2/9 일치로 그대로다.

## 3. motion contact만 복원해도 남는 결함

8B unified 전체는 contact 4/9→1/9, entry 1/8→1/8(1개 개선·1개 회귀), space 동일이다. 진입 MAE는 12.094901→13.416369초로 악화했다. entry 0으로 끝난 다섯 사례는 모두 `invalid_fallback_first`다. 유일한 진입 개선 00003의 0도 모델의 “시작부터 진입해 있음” 관찰이 아니라 null 응답의 fallback이다.

V6 motion으로 최종 contact만 덮어쓰면 접촉 손실 3개는 정의상 없어지지만 다음 문제는 그대로다.

- entry와 spatial 이미지는 이미 **8B unified가 고른 잘못된 시간·fallback 시간**으로 만들어졌다. 나중에 contact 숫자 하나를 바꿔도 제시 장면이 바뀌지 않는다. 해결하려던 내부 시점과 최종 시점의 불일치를 다시 도입한다.
- entry 총 성공 수가 같다는 이유로 기존 성공의 손실이나 fallback 우연 일치를 감출 수 없다. 형식 검증과 의미 검증은 다르다.
- space에는 개선이 없고, 방향 개선 두 개만으로 세 출력 전체를 가져올 근거가 없다. 반대로 방향만 골라 또 조합하면 이는 결과를 보고 새 후보를 추가하는 별도 선택이며 이번 동결 실험의 연장이 아니다.

이 혼합이 제출 형식 위반이라는 주장은 하지 않는다. 문제는 의미적 연결과 근거의 독립성이다. 원래 사전 gate 실패는 그대로 유지해야 한다.

## 4. 실행 비용

실제 8B unified 9개 ask 합계는 **338.676553초**, predictor 합계는 **369.313929초**이며 후자는 모델 로딩과 원본 motion scan을 포함하지 않는다. 같은 4B unified ask 130.705404초 대비 약 2.59배, 과거 4B V6 ask 82.902697초 대비 약 **4.09배**다. 최대 reserved VRAM은 약 7.326GiB였고 현재 NF4는 원본8B에서 런타임 양자화한 상태다.

과거 전체 서버 약42분에는 다른 Stage·로딩·입출력이 포함되므로 4.09를 그대로 곱해 서버 시간을 예측하면 안 된다. 반대로 네 호출이라는 이유로 60분을 충족한다고 주장할 수도 없다. 이런 고비용 구조를 공간 개선 없이 방향 두 사례 때문에 채택할 자원 근거는 현재 없다. archived/current 측정 환경과 서버 GPU 차이 때문에 정식 패키지 시간 검증은 별도로 필요하다.

## 권고
