# 실제 도로 화면 재촬영 준비 안내

이 폴더는 취득 준비물이다. V6에서 실제 촬영한 도로 재촬영 영상은 0개이며, `capture_manifest.json`의 빈 records는 의도한 상태다. 검사기와 양식을 만들었다고 촬영·검수·성능 검증이 완료된 것은 아니다. Stage1 모델 변경은 이번 범위에 없다.

## 촬영 전

1. 사용할 도로 원본의 출처와 사용권을 확인한다. 콘텐츠 이용, 디스플레이 재생·재촬영, 대회 평가, 후속 학습, 재배포를 구분해 허용된 용도만 기록한다. 공개 다운로드나 코드 라이선스만으로 영상 권리를 인정하지 않는다. 개인정보가 있는 장면의 공개 범위도 취득 단계에서 결정한다.
2. 기존 public/DLC/comma와 다른 콘텐츠인지 확인한다. SHA가 달라도 재인코딩한 동일 영상일 수 있다. 같은 주행의 인접 구간과 모든 파생본은 동일 `source_group`으로 묶는다. `content_id`는 같은 원본 구간을 나타낸다. 문자열 ID를 바꾸어 독립 자료로 만들지 않는다.
3. 촬영 목록·조건·split과 검증 질문을 결과 전에 고정한다. 정해진 최소 N만으로 일반화를 보장할 수 없다. 앞선 6원천×2카메라×2화면 제안도 소규모 진단 구성 예이며 통계적 충분성을 뜻하지 않는다.
4. 기기마다 안정된 식별자를 부여한다. 원본 카메라, 화면, 재촬영 카메라는 별개다. 제조사/모델과 물리 기기 ID를 함께 기록한다. 기기 미확인은 임의 ID로 메우지 말고 null로 남긴다. 모델 종류 분리가 목표이면 같은 모델의 다른 기기도 같은 holdout 그룹으로 별도 관리한다. 현재 검사기는 기기 ID 중복만 검사한다.

## 실제 촬영과 증거

도로 영상을 실제 디스플레이에 재생하고 다른 카메라로 촬영한 경우만 `physical_display_recapture`다. JPEG, resize, 화면효과 합성, 디지털 화면 녹화는 실제 물리 재촬영 증거가 아니다. 조작 종류는 `synthetic_transform`으로 분리한다. 원본은 `original_camera`이며 센서에서 촬영된 도로 영상의 출처를 보존한다.

촬영에 사용한 원본 파일, 카메라에서 나온 재촬영 원시 파일, 평가에 전달할 파일을 보존한다. codec·해상도·프레임 수·명목 FPS와 실제 시간축 확인 방법을 적는다. 명목 FPS를 실제 PTS 검증으로 쓰지 않는다. 화면 주사율, 플레이어 설정, 카메라 노출/셔터/초점 설정, 조명, 거리와 각도, 화면 테두리 포함 여부, 촬영 시각·담당자도 기록한다. 모르는 설정은 확인 불가로 남긴다.

각 재촬영에는 디스플레이·재생 장면·재촬영 카메라 배치를 확인할 수 있는 사진/영상(`setup_photo_or_video`)과 촬영 기록(`capture_log`)을 별도 파일로 남긴다. 이 증거는 분류기 입력에 추가하지 않는다. 원본에는 출처 기록(`source_provenance`)을 남긴다. 증거 파일도 SHA256으로 묶는다. 영상에서 화면 테두리가 안 보인다는 이유로 원본 라벨을 붙이지 않는다. 클래스는 실제 취득 과정으로 확인한다.

인코딩/해상도가 클래스와 연결되지 않도록 전달 규칙을 양 클래스에 사전 고정하고 raw도 보존한다. 공통 변환이 모아레 같은 증거를 없앨 수 있으므로 변환 후 결과를 모든 촬영 조건으로 일반화하지 않는다. 결과를 본 뒤 쉬운 촬영·파일만 골라 목록을 바꾸지 않는다.

## 양식과 사람 검수

`record_template.json`은 필드 양식일 뿐 실제 자료가 아니다. 한 파일당 한 record를 `capture_manifest.json`의 records에 넣는다. null을 추측으로 채우지 않는다. `status`는 planned → acquired → human_verified로 기록한다. 자동 검사나 AI 시각 평가는 사람 검수를 대신하지 않는다.

- `record_id`: 평가 파일별 고유 ID. `parent_original_id`: 재촬영의 대응 원본 record ID. 원본은 null.
- `source_group`, `content_id`: 파생본·인접 주행 원천 관계. 원본과 재촬영에서 같은 값.
- `original_camera_id`, `display_id`, `recapture_camera_id`: 물리 기기 식별자. 원본의 뒤 두 값은 null.
- `domain`: road/document/other. `acquisition_kind`: original_camera/physical_display_recapture/synthetic_transform/unknown. `label`: ORIGINAL/RERECORDED/UNKNOWN.
- `split`: development/holdout/unassigned. 원본과 모든 대응 재촬영은 같은 split. holdout은 결과·예측을 보지 않은 검수자 기록을 요구한다.
- `path`, `sha256`: manifest 폴더 아래 파일 상대경로와 소문자 SHA256. 기존 원본을 이동하지 않고 나중에 합법적인 취득 파일을 이 자료 폴더 아래 배치한다.
- `media`: 실제 codec, width, height, decoded_frame_count, nominal_fps, timing_basis, delivery_transform, raw_asset_path/SHA. 검사기는 수치 메타데이터의 진위를 디코딩하여 확인하지 않는다.
- `rights`: verified/pending, 권리 근거 basis, permitted_uses 목록, 재배포 허용 여부, attribution. 프로토콜의 required_use 기본값은 competition_evaluation이다. 학습 용도로 바꾸려면 별도 권리를 확인한다.
- `evidence`: `{"kind":"capture_log","path":"evidence/....json","sha256":"..."}` 형태. 재촬영에는 setup_photo_or_video와 capture_log가 둘 다 필요하다.
- `annotation`: reviewer, reviewed_at, label_basis, model_predictions_seen. holdout 검수 시 마지막 값은 false여야 한다.

protocol의 `frozen_at`, `selection_rule`은 실제 사전 고정 시각과 선택 규칙으로 채운다. `device_holdout_fields`의 각 ID는 development/holdout 간 중복이 없어야 한다. 양쪽 split 중 하나가 비어 있으면 기기 분리 검증 자체는 미측정이다. 이미 사전학습에 노출된 콘텐츠를 새 split으로 나눠도 노출은 취소되지 않는다.

## 검사 실행과 판독

프로젝트 루트에서 다음과 같이 실행한다. 원본·모델은 읽거나 변경하지 않고 지정 manifest와 그 아래 증거 파일만 읽는다. report는 기존 파일을 덮어쓰지 않는다.

```powershell
.\.venv\Scripts\python.exe research/v6_stage1/check_capture_manifest.py research/v6_stage1/capture_manifest.json --report research/v6_stage1/readiness_report.json
```

`NOT_READY`와 종료 코드 2는 자료 누락·충돌 또는 메타데이터 전용 검사 결과다. 현재 빈 manifest는 반드시 이 결과여야 한다. 준비 상태를 확인한 경우에도 결과명은 `METADATA_CHECKS_PASS`이며 성능 PASS가 아니다. 파일 SHA, lineage, split, 권리·검수 기록의 존재만 확인한다. 허위 기록, 잘못된 기기 별칭, 의미상 중복, 실제 디코딩, 권리 해석, 물리 촬영 진위는 별도 사람 검수와 근거가 필요하다. 메타데이터만 있는 `--metadata-only`는 항상 NOT_READY다.

다음 원인 진단에서는 pT/pF/0.5 결합을 모두 동결하고, 실제 재촬영의 결합 미검출을 “TPO는 검출했으나 결합에서 소실”과 “TPO도 미검출”로 분리한다. 원본 오탐도 함께 기록한다. 양성 부족을 합성 자료로 메우거나, 자료 취득만으로 새 모델의 제출 채택을 정당화하지 않는다.
